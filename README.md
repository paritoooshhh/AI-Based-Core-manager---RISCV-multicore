# RISC-V AI Core Management

An experimental project that combines a RISC-V processor implemented in
Verilog with RTL simulation, benchmark-data generation, and a Random
Forest model for deadline-aware core selection. The repository also
includes a matrix-multiplication UI integration.

## Project overview

The project explores how workload characteristics and execution
deadlines can guide the selection of 1--4 processor cores.

The workflow is:

1.  **Verify the RTL:** run testbenches for arithmetic instructions,
    edge cases, memory operations, branches, and multicore workloads.
2.  **Collect benchmark data:** simulate different workload families,
    sizes, and requested core counts.
3.  **Prepare training examples:** derive core-selection labels using a
    deadline-aware policy.
4.  **Train and evaluate the model:** use a scikit-learn Random Forest
    classifier.
5.  **Inspect results:** review simulation logs, benchmark metrics, and
    the evaluation report.

> **Important:** The scheduler is an experiment in policy imitation. The
> reported model accuracy measures agreement with labels generated by
> the project's policy; it does not prove globally optimal scheduling or
> measured hardware power savings.

## Main components

### RTL and testbenches

The RTL describes the RISC-V core and multicore/workload systems.
Testbenches exercise instruction behavior and inspect outputs and
activity counters, including cycles, instructions, ALU operations,
loads, stores, branches, and taken branches.

The PowerShell runner `run_all_testbenches.ps1` is intended to compile
and run testbenches with Icarus Verilog. Review the script and the
testbench output if a test fails; a compile error can indicate a missing
RTL dependency, duplicate module definition, or incorrect source
selection.

### Benchmark dataset

The heavy-workload benchmark covers four workload families:

-   Arithmetic
-   Branch-heavy
-   Memory-heavy
-   Mixed

The benchmark configuration described by the training script uses nine
workload sizes: `8, 16, 32, 48, 64, 96, 128, 192, 256`, with requested
core counts `1, 2, 3, 4`. That gives **4 × 9 × 4 = 144 configurations**
when all cases are present and valid.

The training script expects the benchmark CSV at:

``` text
data/heavy_workload_dataset_144.csv
```

Its required columns include workload type and size, requested cores,
elapsed cycles, result correctness, instruction/ALU/load/store/branch
counts, and branch-taken count.

### Deadline-aware Random Forest model

`train_deadline_core_scheduler_144.py`:

-   Reads and validates the 144-row benchmark CSV.
-   Builds supervised examples for deadline ratios `0.90`, `0.75`,
    `0.50`, and `0.30`.
-   Uses one-core elapsed cycles as the baseline for each workload and
    size.
-   Applies a deadline-aware selection policy that considers assumed
    power and elapsed cycles.
-   One-hot encodes workload type and standardizes numeric features.
-   Trains a `RandomForestClassifier` with 300 trees and
    `random_state=42`.
-   Evaluates on workload sizes `48`, `96`, and `192`, held out from the
    evaluation training split.
-   Trains a final deployment candidate on all generated examples and
    saves it as a Joblib artifact.

The script is configured to write:

``` text
ml/models/deadline_core_scheduler_144.joblib
ml/deadline_scheduler_144_report.txt
ml/deadline_scheduler_examples_144.csv
```

The assumed power values are `0.325 W` per core, scaled linearly for
1--4 cores. These are modeling assumptions, not measurements from
physical hardware.

## Requirements

Install or make available:

-   Windows PowerShell
-   Python 3
-   Icarus Verilog (`iverilog` and `vvp`)
-   Python packages: `pandas`, `scikit-learn`, and `joblib`

## Setup and run (Windows PowerShell)

Open PowerShell in the repository root.

### 1. Check the tools

``` powershell
python --version
iverilog -V
vvp -V
```

If `python` is not recognized, install Python 3 and enable it on `PATH`.
In Windows PowerShell, do not use the Linux command
`/usr/bin/env python3`.

### 2. Install Python dependencies

``` powershell
python -m pip install pandas scikit-learn joblib
```

### 3. Run the RTL testbenches

``` powershell
.\run_all_testbenches.ps1
```

If PowerShell blocks the script due to execution policy, you can run it
for the current process with:

``` powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\run_all_testbenches.ps1
```

Use the logs generated by the runner to inspect individual compile and
simulation results. The exact command-line options and log locations are
defined in the script.

### 4. Generate or place the benchmark CSV

Ensure the completed benchmark dataset is available at:

``` text
data/heavy_workload_dataset_144.csv
```

If your dataset-generation script is stored elsewhere or has a different
filename, run that script first and confirm that it creates this CSV at
the expected path. The training script stops if the file is missing,
does not contain the required columns, contains incorrect benchmark
results, or does not have exactly 144 rows.

### 5. Train and evaluate the scheduler

``` powershell
python .\train_deadline_core_scheduler_144.py
```

On success, the script prints the evaluation report and the locations of
the model, report, and generated examples. It does **not** overwrite a
separate original model; it writes the expanded model to
`ml/models/deadline_core_scheduler_144.joblib`.

### 6. Evaluate unseen workload sizes

``` powershell
python .\evaluate_unseen_workload_sizes.py
```

Check the script's inputs and options before running if your local copy
has been customized.

## Understanding the reported evaluation

The training script evaluates on examples derived from workload sizes
`48`, `96`, and `192`. Its accuracy is compared with the core-selection
labels produced by the deadline-aware policy.

A reported accuracy of **75% (36 out of 48 held-out examples)** means
the model matched 36 of those 48 policy-generated labels. It is not a
guarantee that the selected core count is globally optimal, nor does it
establish actual energy savings. RTL validation of the final model is a
separate step.

## Troubleshooting

-   **`/usr/bin/env` is not recognized:** use `python script_name.py` in
    Windows PowerShell.
-   **Unknown module type during compilation:** check that the RTL file
    defining that module is included in the compile source list.
-   **Duplicate module declaration:** ensure two RTL files defining the
    same module are not compiled together. Use the intended
    implementation (for example, the corrected Zeta file if that is the
    one selected for the project).
-   **Dataset not found:** verify the CSV path relative to the
    repository root.
-   **Dataset validation fails:** check the row count, required column
    names, result-correctness field, and that each workload/size group
    includes core counts 1--4.
-   **Model package errors:** install the required Python packages in
    the same Python environment used to run the script.

## Limitations

-   The model learns from labels generated by a heuristic policy.
-   Power values are assumptions rather than measured physical power.
-   Held-out workload sizes test generalization only within this
    benchmark setup.
-   A trained Joblib file should be loaded only from a trusted source,
    since Joblib/pickle-based artifacts can execute code during
    deserialization.
-   A successful simulation or model evaluation does not by itself
    establish performance on physical hardware.
